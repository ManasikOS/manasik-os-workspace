# Dynamic Roles & Permissions

Replaces the fixed 7-role, code-defined capability matrices in `lib/access/*.ts` with a
database-backed model: any number of roles per agency, every one of them (including the 7
existing built-ins) renameable and deletable except the built-ins themselves, and every
capability of every module — not a generic CRUD subset, the actual ~250 flags each module's
TypeScript interface already defines — toggleable per role from the UI.

**Status: schema + role management + editor UI shipped. Live enforcement wired for the Team
module only. The other 13 modules still read their old hardcoded matrix — see §4.**

## 1. Architecture

- **Enforcement stays application-layer only.** None of the ~50 existing RLS policies were
  touched. Every one of them still reads `current_staff_role()`, which still reads
  `staff_profiles.role` (text), completely unchanged.
- **`staff_roles`** — one row per role per agency. `base_role` is the RLS-recognised tier
  (`ADMIN`/`CEO`/`FINANCE`/`MARKETING`/`OPERATIONS`/`VISA`/`GUIDE`) every role — including a
  brand-new custom one — must declare at creation. That's what makes app-layer-only enforcement
  work without an RLS rewrite: a custom role's fine-grained permissions can be more restrictive
  than its `base_role` tier allows, never more permissive at the raw database level. `is_system`
  is true for the 7 seeded roles — editable (rename, re-describe, edit permissions), never
  deletable, so there is always at least one assignment target and permissions fallback per tier.
- **`role_permissions`** — one JSONB row per `(role, module)`. The JSON keys mirror the module's
  `Capabilities` TypeScript interface exactly (see `lib/access/*.ts`), not a generic
  create/read/update/delete shape — `waiveRequirement`, `approveDiscounts`,
  `configureThresholds` and every other bespoke flag across the 14 modules is just as editable
  as any CRUD-shaped one.
- **`staff_profiles.role_id`** (new column) is the dynamic assignment. `staff_profiles.role`
  (text, unchanged) is kept in sync automatically by a trigger
  (`sync_staff_profile_role_text`) that derives it from the assigned role's `base_role` — so
  every mutator that already writes `role_id` never has to remember to also write `role`.
  `agency_members` gets the identical treatment.
- **Seed data has zero manual-transcription risk.** The 7 system roles' `role_permissions` rows
  were generated by importing the actual, live `capabilitiesFor*()` functions from
  `lib/access/*.ts` and calling them for real (see the migration's header) — not hand-typed —
  so every existing account's permissions are byte-for-byte identical to what they were before
  this migration runs. Nothing regresses on day one; only editing changes anything.

## 3. What's live today

- **Role management**: create a custom role (choose a name + a `base_role` tier; it starts with
  that tier's current permissions, copied, ready to adjust), rename/re-describe any role
  including the 7 built-ins, delete a custom role (blocked while anyone is still assigned to
  it), all from **Team → More → Manage Roles & Permissions**.
- **Permission editing**: every one of the 14 modules' full capability set, toggle by toggle,
  per role.
- **Live enforcement — Team module only.** `app/(main)/management/team/actions.ts`'s
  `currentActor()`, and both `page.tsx` / `[userId]/page.tsx`, now call
  `loadDynamicCapabilities()` instead of the bare `capabilitiesForTeam(role)`. Toggling
  `inviteStaff` off for a role in the editor takes effect on that role's very next Team Server
  Action — verified by reading the actual call sites, not assumed.

## 4. What's not done — the other 13 modules

Departure Groups, Documents, Finance, Leads, Operations, Packages, Pilgrims, Reports, Settings,
Suppliers, Visa, AI Agent and Inbox each still call their own `capabilitiesFor*(role)` directly,
reading the old hardcoded switch. Their `role_permissions` rows are fully populated and fully
editable in the UI right now — editing them has no runtime effect yet outside Team.

The mechanical fix, identical for each module (using Team as the template):

1. Wherever that module resolves `const can = capabilitiesForX(role);`, first fetch `roleId`
   from `getCurrentStaffRole()` (already returns it) and a `db` client, then:
   `const can = await loadDynamicCapabilities(db, roleId, "<module_key>", capabilitiesForX(role));`
2. That call site's containing function must be (or already is) `async`.
3. Repeat for every call site in that module — Team needed 3 (`actions.ts`, `page.tsx`,
   `[userId]/page.tsx`); most single-page modules will need fewer.

This was scoped out of the initial pass deliberately rather than rushed across 13 modules
untested — each is real, working code with its own Server Actions and pages; wiring all of them
in one pass without individually verifying each is how a permissions system gets a silent hole
in it. Team was chosen as the first (and proof) because it was already the module under active
work this session.

## 5. Verification

```bash
npx tsc --noEmit && npx eslint .
```

Both pass clean on every file this feature touched. No test harness exists in this repo (`lint`
and `typecheck` only), so functional verification is manual:

1. **Apply the migration** (see §6 — this alone is a prerequisite, same as every other migration
   built this session).
2. Open **Team → More → Manage Roles & Permissions**. Confirm all 7 system roles list, each
   shows real (non-empty) permissions per module matching today's actual behaviour.
3. Create a custom role based on GUIDE; toggle `team.viewWorkload` on for it.
4. Assign that role to a test account (once role assignment is wired into the invite / change-role
   UI — see §7).
5. Sign in as that account; confirm the Tasks & Workload tab is now visible on Team, where a
   plain Guide wouldn't see it — proves the Team-module enforcement pipeline end to end.

## 6. ⚠️ This migration must be applied manually

Exactly like every other migration built in this session (see
`docs/team-module-remediation-plan.md`), **nothing in this feature works until
`supabase/migrations/20260924090000_dynamic_roles_permissions.sql` is applied to the live
database** — via the Supabase Dashboard SQL Editor, or `supabase db push` with the project's
database password. There is no tooling available in this environment to apply it automatically.

## 7. Explicitly out of scope (for now)

- **Assigning a staff member to a brand-new custom role** through the Invite dialog or the
  Change Role dialog — those still pick from the fixed 7-role list (`ROLE_LABELS`). The
  repository function (`assignStaffRole()`) and its Server Action (`assignStaffRoleAction`)
  exist and work; wiring them into those two dialogs' role pickers is the next piece.
- Runtime enforcement for the 13 non-Team modules (§4).
- Per-user permission overrides on top of a role (this system is still role-based, not
  per-person — matches the product decision already on record in
  `docs/team-module-remediation-plan.md` §8).
